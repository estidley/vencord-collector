# Security and lifecycle boundaries

## Encryption at rest

Message storage is an envelope containing the entire vault, plus a monotonically increasing storage revision. Explicit always-on setup additionally persists an OS-encrypted automatic-unlock record, described below. AES-256-GCM authenticates the encrypted message text, IDs, provenance, permissions and local audit. PBKDF2-SHA256 derives a non-extractable in-memory key using a random 16-byte salt and 600,000 iterations. Every save uses a fresh 12-byte IV. Algorithm/context/version/KDF parameters are authenticated, and unexpected parameters fail before decryption.

Manual/timed use persists no passphrase. Explicit always-on setup stores a second encrypted IndexedDB record containing the passphrase, account ID and ongoing permission ID, protected by Windows DPAPI through Electron `safeStorage`. This record is encrypted before crossing back into renderer storage. The native helper checks the requested account before releasing a credential. No plaintext fallback is permitted; non-Windows or unavailable OS encryption rejects always-on setup. No plaintext index, telemetry, Discord credential or error dump is stored. Short passphrases are rejected, but length alone does not guarantee strength. JavaScript cannot guarantee memory zeroization or protection from swap/crash dumps.

Windows DPAPI protects against other Windows users, not other software running as the same user. A compromised Discord renderer or plugin may call the native bridge and obtain the remembered passphrase. Always-on intentionally trades manual unlocking for that trust boundary. See [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage). No recovery guarantee is made if the OS profile or protected record is lost; keep your original password.

## Trust boundaries

This protects a locked buffer against casual file inspection; it is not isolation from malicious code running in the same browser/Discord renderer, other extensions/plugins, malware, DevTools, or a compromised OS. The Vencord panel shares the client's trust boundary. The independent app avoids depending on that renderer but still trusts its browser profile and machine.

User-supplied metadata and consent attestations are not externally verified. A passphrase holder can modify/re-encrypt records. The bounded encrypted audit is operational history, not an append-only, independently verifiable compliance log. Failed attempts do not persist content or raw errors; no assertion is made that every denied action is durably audited. A future server must supply authenticated, durable access auditing.

The offline page's CSP denies network connections and remote resources. Its static server binds only 127.0.0.1:4317 by default (`COLLECTOR_PORT` can select another loopback port), checks Host, serves two known files, denies non-GET requests, and cannot read arbitrary paths. The plugin performs no network calls unless receiver sync is armed; then only its native helper contacts `127.0.0.1:<configured port>` with the importer token, never another host. It cannot impose its offline CSP on Discord.

**Receiver sync trust boundary.** The token and generated transfer passphrase are decrypted only in the Electron main process, but `safeStorage`/DPAPI protects them from offline file copying, not from malware running as the same Windows user. Any code that can drive the plugin's renderer (Discord itself, another plugin, a renderer exploit) can ask the native helper to deliver batches for the configured permission, and can already forge captured events; the receiver's scope checks bound what it accepts, not whether a message is genuine. Synced text from other people is untrusted: receiver MCP tools are read-only and mark results untrusted, and any future agent that writes (calendar, messages) must require the owner's confirmation rather than act on message text.

Always-on holds the vault key in memory while Discord is open and resumes automatically for the accepted account after restart. Optional timed sessions still end after one hour and never resume automatically. File-only use retains five-minute idle/hide/close locking. Stop removes the protected auto-unlock record and drops the key; plugin disable also removes it. Closing/reloading Discord preserves the opted-in auto-unlock record. Logout/account changes lock immediately; returning to the accepted account may restore its existing permission. Capture failures pause the current runtime rather than retrying indefinitely. If removal of a remembered record fails, the UI says so; disable the plugin before restarting and retry. The plugin has no global indicator outside settings.

The all-conversations option is a broad permission over every supported conversation and sender delivered to the account, including newly joined channels. It requires authority and risk attestations, defaults to local-only storage and seven-day retention, and cannot be mixed with selected capture in the same session. This increases the amount of sensitive data held while unlocked. A participant-membership change stops selected scope; account scope intentionally includes new participants. It does not prove anyone's consent or waive platform rules.

## Retention, concurrency and deletion

Ordinary permissions expire within 30 days. Continuous live permissions explicitly have no expiry until revoked; they cannot be used for file imports. Retained records still expire after the configured 1–30 days (default seven), capped by any permission expiry. Edits do not extend retention. Expired records are inaccessible through export and removed on unlock or mutation/prune. A locked/closed app has no cleanup job: expired ciphertext may remain until opened. No physical secure-erasure guarantee is made for browser storage, snapshots or backups.

Revoking a permission removes its message and activity records from the current vault, disables export and retains minimal permission/audit metadata. Independent permissions can contain independent copies; revoke each applicable permission. Prior exported files and original input files remain outside this vault and require separate deletion. Downloading a handoff is not a verified successful ingestion.

An IndexedDB transaction compares storage revision before saving to prevent silent overwrites across tabs. Conflicts fail with an instruction to lock/unlock. In-flight operations are mutually exclusive per controller; locking cancels operations before their storage transaction begins. A transaction already started may complete, but the key remains dropped and the operation does not return a plaintext result after a lock. No automatic retries run in the background.

Live edits replace older live text. Observed deletes remove matching buffered records across permissions/sources and leave only a known-sender tombstone. Source files, downloaded exports, backups and offline deletions remain outside this guarantee. See [CONNECTOR.md](CONNECTOR.md) for receiver responsibilities.

Capacity is bounded. The queue accepts at most 1,000 pending events / 2 MiB serialized event text; the vault holds 5,000 message records plus 2,000 activity observations / 8 MiB total plaintext. Continuous mode rolls out the oldest records belonging to its own permission and records `capacity-prune` audits. It never evicts unrelated imports; those can still leave insufficient space. Removing a tombstone by retention/rollover also removes its replay suppression. Each save re-encrypts the whole vault. High-volume traffic, full disk, concurrent writers or queue overflow may still stop capture. This is not an unlimited or lossless archive. After 100 permission records a new profile is needed; automatic restarts reuse the existing grant rather than creating one each time. Receiver authorization and SQL/search remain separate work.

## Activity and cached selections

Activity categories default off, including when decoding old vaults. Enabling them requires separate category/server/person choices. Presence scopes are account-visible selected users, not proof of a server login. Activity scope reductions delete observations no longer permitted. Activity export requires its own allow flag and explicit handoff confirmation. Activity has a separate bounded queue (250 observations / 512 KiB), shares the encrypted vault and retention controls, and rolls out only its own oldest activity entries. It never evicts message records. Cache absence is never interpreted as an event cancellation or user logout.

The loaded-message button reads only the selected, permitted channel cache and requires review/confirmation. Cached snapshots cannot overwrite an existing live version or retained deletion tombstone. A snapshot can contain stale cache data; it is not authenticated history. Event text is untrusted data and must not instruct a future AI receiver. No notifications or AI actions execute here.

## Reporting

Report implementation issues to the repository owner privately and include synthetic reproduction inputs only. Never attach your message files, passphrase, exports, or account credentials to issue reports. An operating bot/service will need a published user support and abuse-reporting channel before deployment.
